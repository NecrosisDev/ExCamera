Install this complete source tree, retaining its paths (including tools/ and .github/workflows/). To update an existing checkout, overlay this tree while preserving .git and your own edits.

1. Set `FP_BUILD` in src/build_identity.h to the new version and advance `FP_REVISION`. Then build and test locally. A push to main whose `FP_BUILD` has no tag yet publishes automatically, so finish testing before that push. See docs/RELEASE_CHECKLIST.md. Build runs on relevant main/PR changes; Release runs on v* tag pushes and on the workflow dispatch that Auto release uses. Both check generated compatibility tables, compile the Windows runtime, check DLL exports and validate the runtime ZIP without a game executable. The public release does not ship test binaries or a test runner; the parked rebuild tests are not part of this workflow.
2. Commit the release source with a meaningful message.
3. Publish in one of two ways:
   - Automatic: push the commit to main. Auto release creates the v<FP_BUILD> tag and starts Release when the tag does not exist.
   - Manual tag: create the tag and push it with main so Auto release sees the tag and skips. For example:

     git tag -a v0.3.1 -m "ExCamera v0.3.1"
     git push origin main v0.3.1

Use your chosen version in both commands. Future tags can be v0.3.1, v0.3.2, v1.0.0, etc. Valid tags are vX.Y.Z with an optional SemVer prerelease suffix (for example v0.3.1-rc.1). Numeric version/prerelease identifiers cannot have leading zeros. Build metadata (+...) is intentionally unsupported. Prerelease tags create GitHub prereleases.

The workflow checks out and verifies the exact tag commit. It derives FP_BUILD from the tag before compiling the launcher and DLL, preserving FP_REVISION. This edits only the ephemeral CI checkout, not your committed header. Local builds still use the checked-in FP_BUILD. The release title and ZIP filename follow the tag version. Immediately before publication, an authenticated read rechecks the remote tag commit against the built commit and stops on a mismatch or API error. This narrows the tag-movement race; keep release tags immutable.

Release notes are generated automatically from Git commit subjects since the prior reachable valid version tag selected by git describe, including direct commits and merges, with links to commits and a full comparison. Selection uses Git's bounded candidate search, not version-number sorting or a guarantee of the globally closest tag. The first release lists the initial history. Write meaningful commit subjects; this is a commit changelog, not a claim that changes were gameplay-tested. No manual release-note editing or pull request is required. The supplied CHANGELOG.md separately describes the explicit 0.2.0 source-baseline comparison; the workflow does not copy that document into generated release notes.

Publication happens only after generated-table validation, compilation, DLL export checks, exact ZIP-contents validation, and artifact upload succeed. Do not manually create the release first. No personal token is required; the release job uses GitHub's built-in token with contents: write. The ordinary Build workflow has read-only permissions.

If a tag or release already exists, stop and inspect it rather than force-moving or overwriting it. Failed checks before publication can be rerun normally from Actions once their cause is understood; source fixes require a new commit and new tag. A publish/upload failure may leave a draft or published release: inspect Releases and the Actions log before retrying. The workflow never overwrites an existing release and does not force-create missing tags.

Local script/package-fixture checks do not validate Windows/MSVC or gameplay. This workflow must still be exercised on GitHub and the resulting binaries tested in the supported game.

Local builds stage and validate before publishing. A failed build normally retains the previous outputs; those files are not evidence that the latest build succeeded. Close the game/launcher before rebuilding. If publication rollback fails, keep the recovery directory named in the error and do not use the incomplete outputs. Runtime-file publication is not crash-atomic; the ZIP is replaced individually only after it is complete. Building without --package does not refresh an existing ZIP. Package verification checks integrity and contents, not latest-attempt freshness.
